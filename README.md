# PQ 공고 자동 수집 시스템 (재구축판)

지자체·공기업·조달청 등 다수 발주처 게시판을 자동으로 순회해 조건에 맞는 공고를
찾아 구글 시트에 쌓고, Streamlit 대시보드에서 검토하는 시스템.

기존 저장소(`main.py` / `main_major.py` / `main_max.py` / `main_pure.py` 4벌)를
분석한 뒤, **단일 엔진 + 자동 단계 상승(escalation) 구조**로 다시 짰다. 자세한
문제 진단은 대화 중 전달한 `project_overview.md`를 참고.

## 폴더 구조

```
app.py                  # Streamlit 대시보드 (UI 전용)
main.py                 # 수집 실행 진입점 (CLI / GitHub Actions / app.py에서 subprocess로 호출)
config.py               # 설정값 + 시크릿 로딩 (하드코딩된 비밀번호/키 없음)
storage.py              # 구글 시트 읽기/쓰기 전담
site_registry.py        # 명부 엑셀 + URL 오버라이드로 '수집 대상 목록' 구성
engine.py               # 사이트별 자동 단계 상승(오케스트레이션) + 병렬 실행
scrapers/
  base.py               # 공통 파싱 로직 (행 파싱, 첨부파일 딥스캔)
  generic_requests.py   # 2순위: requests + BeautifulSoup
  generic_selenium.py   # 3순위: 범용 Selenium
  api_g2b.py            # 1순위: 나라장터 Open API
  custom/
    khnp.py             # 4순위: 한국수력원자력 K-Pro 전용 (팝업닫기→메뉴클릭→대기→클릭)
    igunsul.py           # 4순위: 아이건설넷 로그인 전용
utils/
  logging_setup.py      # 실행 로그 (콘솔 + 구조화된 RUN_LOG, 실패 원인 추적용)
  date_parser.py         # 텍스트 안 날짜 추출
.github/workflows/auto_run.yml   # 수동 실행용 GitHub Actions
.streamlit/secrets.toml.example  # 로컬 개발용 시크릿 템플릿 (실제 값은 커밋 금지)
```

## 이전 구조 대비 무엇이 바뀌었나

1. **엔진 4개 → 1개**: 더 이상 "빠른/정밀/극한/주요4대"를 사람이 고르지 않는다.
   `engine.py`가 사이트별로 `requests → (실패 시) selenium → (그래도 실패 시) 수동확인`
   순서를 자동으로 시도한다. 이전 버전은 대시보드 라디오 버튼 기본값이 Selenium이
   전혀 없는 "빠른 탐색"이라, 별도로 바꾸지 않으면 JS 렌더링이 필요한 사이트가
   전부 조용히 누락됐다 — 이 문제 자체가 구조적으로 사라진다.
2. **KHNP 등 '자체 시스템형' 사이트 전용 처리**: `scrapers/custom/khnp.py`에
   말씀하신 흐름(팝업 닫기 → 입찰공고 메뉴 → 입찰공고조회 → 대기 → 클릭)을
   구현했다. **다만 이 사이트는 봇 방어가 강해 실제 DOM을 확인 못 하고 화면
   캡처만으로 작성했다.** 처음 실행해보면 셀렉터 조정이 필요할 가능성이 높은데,
   실패해도 이제는 `run_log`에 "어느 단계(팝업/메뉴클릭/대기/파싱)에서 막혔는지"가
   정확히 남으므로, 그 로그를 보고 한 부분만 고치면 된다.
3. **침묵의 에러 제거**: `except: pass`를 없애고 `log_failure()` / `log_manual_required()`로
   통일했다. 실행 후 대시보드의 "🚨 수동 확인 필요" 메뉴에서 실패 원인을 바로 볼 수 있다.
4. **자격증명 하드코딩 제거**: 아이건설넷 계정, 조달청 API 키, 대시보드 비밀번호를
   전부 `config.get_secret()`으로 옮겼다 (환경변수 → Streamlit secrets 순으로 탐색).
   **기존에 코드에 평문으로 있던 값들은 git 히스토리에 이미 노출되어 있으니, 여유
   되실 때 실제 비밀번호/키 자체를 교체하시는 걸 권장한다.**
5. **GitHub Actions 워크플로우 수정**: `google_key.json`을 만드는 단계가 아예
   없어서 기존 워크플로우는 실행될 때마다 구글 시트 연결 단계에서 실패하고
   있었다. 이번에 시크릿에서 키 파일을 만드는 단계를 추가했고, 존재하지도 않는
   파일(`verified_sites.json`, `저장된_공고모음.xlsx`)을 커밋하려던 죽은 단계는 제거했다.
6. **실패 원인 시각화**: 신규 구글시트 탭 `run_log`(실패 로그), `manual_check`
   (자동화 포기 목록)를 만들고, 대시보드에 "🚨 수동 확인 필요" 메뉴로 노출했다.

## 배포 전 설정할 것 (필수)

### 1) 구글 시트
기존과 동일하게 `맞춤공고_DB`라는 이름의 구글 스프레드시트를 그대로 쓰면 된다.
아래 탭이 필요하다 (없으면 코드가 자동 생성하는 탭도 있지만, `notices`/`collected_orgs`는
최초 1회 직접 만들어두는 걸 권장):
- `notices` (헤더: 출처, 등록일, 공고제목, 상세링크, notice_key, 등록시각, 특이사항, 검토유무)
- `collected_orgs` (헤더: org_name)
- `url_overrides` (헤더: 발주기관명, 정확한_게시판_URL, 비고) — 없어도 동작함
- `settings`, `run_log`, `manual_check` — 없으면 코드가 자동 생성

### 2) 시크릿 등록
`.streamlit/secrets.toml.example`을 참고해서:
- **Streamlit Cloud**: 앱 Settings → Secrets에 붙여넣기
- **GitHub Actions**: 저장소 Settings → Secrets and variables → Actions에
  `GOOGLE_CREDENTIALS`, `G2B_API_KEY`, `IGUNSUL_ID`, `IGUNSUL_PW` 등록

### 3) 로컬 테스트
```bash
pip install -r requirements.txt --break-system-packages
cp .streamlit/secrets.toml.example .streamlit/secrets.toml   # 값 채우기
streamlit run app.py
```

## 최신 업데이트 (전수조사 결과 반영)

실제 84곳 전수조사 로그를 분석한 결과, **59곳(70%)이 '클라우드 IP 차단'으로 실패**했습니다.
차단된 곳들을 계열별로 보면 지방해양수산청·유역환경청·지방국토관리청 등 중앙부처
지방청과 새올 시스템을 쓰는 시/군/구청이 집중적으로 막혀 있고, 공사·공단 계열
(대전도시공사, LH, 국가철도공단 등)은 대체로 잘 됩니다. 개별 사이트가 각자 막는 게
아니라 **정부통합전산센터/새올 시스템처럼 여러 기관이 공유하는 인프라 단위로
클라우드 IP 대역을 차단하고 있는 것으로 보입니다.**

**결론**: README 상단에 적어둔 "국내 IP 우회" 표의 방법 중 하나를 실제로 도입할
시점으로 보입니다. 70%가 막히는 상황에서는 코드 개선만으로는 한계가 있습니다.

이번에 추가로 반영한 것:
1. **불필요한 재시도 제거**: 접속 자체가 막힌 사이트는 requests든 selenium이든 같은
   네트워크 경로로 나가므로 selenium 재시도도 똑같이 막힌다. 이제 requests 단계에서
   '연결 자체 실패'가 확인되면 selenium 재시도를 건너뛴다 (사이트당 30~50초 절약 -
   차단된 사이트가 많을 때 전체 실행 시간이 크게 줄어듦).
2. **연결 타임아웃 단축**: `requests`의 타임아웃을 (연결 5초, 읽기 20초)로 분리.
   접속 자체가 안 되는 경우 20초까지 기다리지 않고 5초 만에 실패 판정.
3. **진행률 표시줄(프로그레스 바) 추가**: "공고 자동수집" 화면에 가로 막대형
   진행률 바가 생겨서, 지금 몇 곳 중 몇 곳을 처리했는지 실시간으로 보인다.
   전수조사처럼 오래 걸리는 작업에서 얼마나 남았는지 보고 기다릴지 판단할 수 있음.



1. **한국수력원자력 바로가기 링크 수정**: `https://khnp.co.kr`(도메인 루트, 안 열림)
   → `https://ebiz.khnp.co.kr/login.do`(실제 K-Pro 로그인 화면)로 수정.
   `config.KNOWN_HARD_SITES`에 `label`/`url`/`reason`을 함께 관리하도록 구조 변경.
2. **"수동 확인 필요" → "🔍 실패 로그 분석"으로 명칭 변경** (사이드바 메뉴, 페이지 제목 등
   화면에 보이는 문구 전체). 내부 구글시트 탭 이름(`manual_check`)은 기존 데이터 연속성을
   위해 그대로 유지.
3. **"발주처 URL 관리" 화면을 목록 선택 방식으로 전면 개편**:
   - 기존에는 스프레드시트 형태로 발주기관명을 직접 타이핑해야 했음
   - 이제는 "✏️ 등록된 발주처 수정" 탭에서 명부에 등록된 전체 발주처 이름을
     드롭다운으로 골라서 그 발주처의 URL만 수정/삭제할 수 있음
   - "➕ 새 발주처 추가" 탭에서 명부에 아예 없는 새 발주처를 이름+URL로 추가하면,
     **엑셀이나 코드를 건드리지 않고도** 다음 수집부터 바로 대상에 포함됨
     (`site_registry.py`가 오버라이드 중 기존 명부에 없는 항목을 자동으로 새
     발주처로 추가하도록 수정됨)

## 페이지네이션(다음 페이지) 지원 추가 — 적응형 중지 조건

유성구청 도시계획과처럼 하루에 10건 넘게 올리는 게시판에서 실제로 확인된 문제:
1페이지만 읽다 보니, 다음 수집 사이에 새 공고가 쌓이면 어제 공고가 2페이지로
밀려나서 **영원히 누락**되는 현상이 있었다 (2026-08-26자 "건설공사 안전점검
수행기관 지정 공고[원신흥동 557-1]"가 정확히 이 케이스였음 - 하루 평균 5~13건씩
올라오는 게시판에서 해당 날짜만 0건으로 완전히 비어 있었다).

처음에는 "무조건 2페이지 더 본다"는 고정 방식으로 고쳤는데, 사용자 피드백으로
더 나은 방식으로 재설계했다: **페이지를 고정된 개수만큼 보는 게 아니라, 이미
저장해둔 공고(notice_key가 history에 있음)나 수집 기간보다 오래된 공고를
만날 때까지 계속 다음 페이지로 넘어간다** (`scrapers/base.py`의
`page_has_stop_signal` / `find_next_page_url`). 게시판은 보통 최신순 정렬이므로,
이미 아는 지점을 만나면 그 아래는 다 예전에 이미 본 내용이라고 보고 멈춘다.

- 하루 5건 올리는 게시판: 1페이지에서 바로 멈춤 (예전과 동일하게 빠름)
- 하루 20건 올리는 게시판: 필요한 만큼(3페이지든 5페이지든) 알아서 더 감
- `config.MAX_PAGINATION_SAFETY_CAP`(기본 8페이지)은 혹시 모를 오작동으로 인한
  무한 루프만 막는 안전장치이고, 정상적인 경우 대부분 1~2페이지에서 멈춘다.

실제 유성구청 사례(8/27 신규 2건 + 8/26 신규 1건 + 8/22 기존 공고를 만나서 중단)를
그대로 재현해 정확히 그 지점까지만 가고 3페이지는 안 가는 것까지 테스트로 확인했다.
안전 상한 자체가 제대로 작동하는지(무한 루프 방지)도 별도로 확인함.

**한계**: 페이지 번호가 `<a href="...">` 형태의 실제 링크로 되어 있는 게시판만
지원한다. `href="#"`이고 `onclick`으로만 페이지를 넘기는 게시판은 이 방식으로는
따라갈 수 없다(자바스크립트 실행이 필요해서, 클릭 자동화까지 붙여야 함 - 필요하면
추후 확장 가능).

## 제목 추출 로직 개선 — '공고번호'와 '제목'이 분리된 게시판 대응

아산시처럼 게시판에 '고시공고번호'(예: 아산시 공고 제2026-3026호)와 '제목'(실제
내용을 설명하는 문장)이 서로 다른 칸에 있고, 링크는 번호 쪽에 걸려있는 사이트가
있다. 예전 코드는 `<a>` 태그 하나의 텍스트만 제목으로 썼기 때문에, 이런 사이트에서는
**번호만 저장되고 진짜 제목은 전부 유실되고 있었다** (실제 데이터로 확인: 아산시
73건 전부 "아산시 공고 제2026-XXXX호" 형태였고 실제 제목이 하나도 없었음).

이제 `<a>` 태그 텍스트 하나만 보지 않고, 같은 행의 모든 셀 텍스트를 후보로 모은
뒤 "OO시 (읍면동) 공고/고시 제OOOO호" 형식만 담은 후보는 제외하고, 남은 것 중
가장 긴(=가장 설명적인) 텍스트를 제목으로 고른다(`scrapers/base.py`의
`_pick_title`). 실제 아산시 데이터로 재현 테스트했고, 기존에 잘 되던 사이트
(보령시, 유성구청처럼 `<a>` 자체가 이미 완전한 제목인 경우)도 회귀 없이 그대로
동작하는 것까지 확인했다.

## 프록시 토글 (무료, 실험적)

"공고 자동수집" 화면에 "🌐 무료 프록시로 우회 시도" 토글이 추가됐다. 켜면 매 실행마다
ProxyScrape의 무료 API(회원가입/키 불필요)에서 한국(KR) IP 프록시 후보를 받아와서,
그중 실제로 살아있는 것 하나를 찾아 이번 실행 동안만 그 프록시로 우회한다.

**작동을 보장하지 않는다는 점을 분명히 밝혀둔다:**
- 여기서 쓰는 건 전부 '무료 공개 프록시'다. 진짜 가정집 회선이 아니라 대부분
  데이터센터/오픈릴레이 서버라서, 지금 우리가 막히는 이유(클라우드 IP 차단)와
  똑같은 이유로 이 프록시들도 막힐 수 있다.
- 무료 프록시는 수명이 짧다(몇 분~몇 시간). 어떤 실행에선 잡히고 어떤 실행에선
  하나도 안 잡힐 수 있다. 실행 로그 맨 위 `[프록시]`로 시작하는 줄에서 이번에
  프록시를 찾았는지, 못 찾아서 그냥 진행했는지 바로 확인할 수 있다.
- 대전 지역처럼 확실한 우회가 꼭 필요한 경우, 무료 프록시보다 회사 사무실
  회선에 GitHub Actions 셀프호스팅 러너를 두는 쪽을 권장한다 (아래 참고) —
  그건 '진짜' 대전 IP라서 프록시 뽑기 운에 기대지 않아도 된다.
- **(실제 실행에서 확인된 것) "IP 차단" 로그가 전부 진짜 차단은 아닐 수 있다.**
  프록시를 거치면 클라이언트→프록시→대상 서버로 홉이 하나 늘고, `https://`
  사이트는 프록시와 CONNECT 터널을 먼저 맺어야 하는데 이 단계도 '연결 타임아웃'
  값을 쓴다. 무료 프록시 자체가 느릴 수 있어서, 원래는 됐을 연결을 "차단"으로
  잘못 판정하는 사례가 실제로 있었다 (에러 메시지에 최종 목적지 이름이 나와도
  실제로는 프록시를 거친 시도였음). 그래서 프록시 사용 중에는 연결 타임아웃을
  5초 → 15초로 자동으로 늘리도록 고쳤다(`config.get_request_timeout_tuple()`).
  그래도 실패하면 그때는 정말 차단일 가능성이 높다.

## 대전 지역(중요도 높음)에 대한 별도 권장 사항 → 두 개의 수집 버튼으로 구현됨

셀프호스팅 러너를 설치한 뒤, 대시보드 "공고 자동수집" 화면에 버튼이 두 개로 늘어난다.

- **🚀 지금 바로 수집 (클라우드)**: 예전과 동일하게 Streamlit Cloud에서 바로 실행.
  빠르지만 클라우드 IP를 차단하는 사이트는 여전히 못 잡음.
- **🏢 사무실 PC로 확실하게 수집**: Streamlit이 직접 실행하는 게 아니라, GitHub에게
  "워크플로우 실행해줘"라고 신호만 보낸다. 실제 실행은 대전 사무실 PC(셀프호스팅
  러너)에서 일어나고, 결과는 **똑같은 구글 시트**에 쌓이므로 대시보드 화면은
  완전히 동일하게 쓰면 된다. 다만 실행이 사무실 PC에서 비동기로 일어나기 때문에
  Streamlit 화면에 실시간 로그가 뜨지는 않고, 대신:
  - 버튼 아래 "🏢 사무실 PC(GitHub Actions) 최근 실행 상태"에서 진행 상태(대기중/
    실행중/완료)를 새로고침해서 확인할 수 있고
  - "GitHub Actions에서 실시간 로그 보기" 링크를 누르면 실제 로그를 볼 수 있다.

**필요한 설정**: `.streamlit/secrets.toml.example`의 `GITHUB_TOKEN`(이 저장소에 대한
Fine-grained Personal Access Token, 'Actions: Read and write' 권한)과
`GITHUB_REPO`("owner/repository" 형식)를 Streamlit Secrets에 등록해야 두 번째
버튼이 활성화된다. 등록 안 해도 첫 번째 버튼(클라우드)은 그대로 잘 동작한다.

**중복 실행 방지 개선**: 예전에는 "지금 실행 중인지" 잠금 관리가 Streamlit
버튼 쪽 코드에만 있어서, 클라우드에서 실행 중일 때 GitHub Actions로도 동시에
실행하면 서로 몰랐다. 이번에 잠금 획득/해제 로직을 `main.py` 안으로 옮겨서,
어느 경로로 실행되든(클라우드/사무실 PC) 같은 구글 시트를 통해 서로의 실행
여부를 확인하고 기다리도록 고쳤다.

**참고**: 완전 자동 스케줄(예: 매일 정해진 시간에 자동 실행)은 일부러 넣지
않았다 — 사용자가 실사용 중 "자동 실행은 트래픽이 몰리면 늦게 도는 경우가 있어
수동이 더 낫다"고 판단해, 지금처럼 버튼을 눌러서 원하는 시점에 실행하는 방식을
유지하기로 했다. 나중에 필요해지면 워크플로우 파일에 `schedule:` 트리거를
추가하는 것만으로 쉽게 켤 수 있다.

(참고로 이 기능을 만들게 된 계기: 대전광역시 산하 6곳(중구·대덕구·유성구·서구·
동구청 + 상수도사업본부)이 두 번의 실행 모두에서 꾸준히 클라우드 IP 차단으로
실패한 것이 확인됐고, 회사가 대전 소재라 이 지역 커버리지가 특히 중요했다.
GitHub Actions 셀프호스팅 러너 비용은 퍼블릭 저장소면 완전 무료, 프라이빗
저장소면 2026년 3월부터 분당 $0.002의 아주 저렴한 비용이 든다.)

## 그 외 국내 IP 우회 옵션 비교 (참고용)

| 방법 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **무료 프록시 토글** (위 기능) | ProxyScrape 무료 API로 매 실행마다 살아있는 KR 프록시를 찾아 사용 | 완전 무료, 코드에 이미 내장됨 | 작동 보장 안 됨, 수명이 짧음 |
| **국내 자체 호스팅 러너** | 사무실 PC/서버에 GitHub Actions 셀프호스팅 러너 설치 | 실제 사무실 회선이라 차단 가능성 가장 낮음, 사실상 무료 | 그 컴퓨터가 항상 켜져 있어야 함 |
| **국내 VPS** | 카페24, 가비아 등 국내 호스팅사의 저가 VPS | 24시간 가동 가능 | 데이터센터 IP라 일부 사이트는 여전히 차단 가능 |
| **국내(KR) 주거용 프록시 서비스(유료)** | Bright Data, Oxylabs 등 유료 KR 주거용 IP | 차단 가능성 가장 낮음 | 트래픽 기준 과금 |

지금 당장은 무료 프록시 토글을 켜서 얼마나 도움이 되는지 몇 번 지켜보고,
대전처럼 중요도가 높은 지역만 셀프호스팅 러너로 확실히 잡는 조합을 권장한다.


- **KHNP 셀렉터 검증 필요**: `scrapers/custom/khnp.py`는 화면 캡처 기반 추정으로
  작성됨. 실제 테스트에서도 `click_menu` 단계에서 실패가 확인됨(예상된 결과) -
  보안이 강한 사이트라 수동 확인 목록에 남기는 것을 권장. (한국수자원공사,
  인천국제공항공사도 비슷한 유형의 전용 입찰시스템으로 보임 - 나중에 여유 있을 때
  KHNP 고치는 김에 함께 검토)
- **일부 사이트는 클라우드 IP 자체를 차단함** (실제 테스트로 확인: 보령시청은
  `ConnectTimeout`으로 접속 자체가 안 됨 - 셀렉터 문제가 아니라 Streamlit Cloud의
  해외/클라우드 IP를 막고 있는 것으로 추정됨). 이런 사이트는 코드로 해결 불가하며,
  국내 IP를 경유하는 별도 인프라(국내 서버/프록시)가 필요함. `manual_check` 사유에
  "클라우드 IP" 문구가 있으면 이 케이스임.
- **iframe 안에 게시판이 있는 사이트 대응 추가됨**: 대전 동구청처럼 메뉴 페이지
  안에 실제 게시판이 다른 도메인의 iframe으로 끼워진 패턴을 실제 페이지 소스로
  확인하고 자동 탐지 로직을 추가함(`scrapers/base.py`의 `discover_additional_boards`).
- **나라장터(G2B) API 400 에러 수정**: 실제 실행 로그에서 `HTTP 400`을 확인 -
  공공데이터포털의 '인코딩' 서비스키를 그대로 넣으면 이중 인코딩되어 발생하는
  흔한 문제. `scrapers/api_g2b.py`에서 키를 한 번 디코딩해서 방어하도록 수정함.
  그래도 400이 계속 뜨면 `run_log`에 응답 본문 일부가 함께 남으므로 원인을 바로
  확인 가능.
- **등록명부 엑셀의 우측 블록**(19번째 열부터 발주처/모집공고일 등이 한 번 더
  반복되는 부분)은 URL 컬럼이 없어 현재 코드에서 수집 대상에 포함하지 않는다.
  이 블록의 기관들을 자동 수집 대상으로 삼아야 한다면 별도 URL 컬럼을 추가하거나
  `site_registry.py`의 로직을 확장해야 한다.
- **"*24년부터 조달청*" 표시 기관**: 실제 데이터로 확인한 결과 16곳 중 7곳은
  자체 게시판에서도 여전히 공고가 잡히고(한국환경공단, 한국농어촌공사 등),
  9곳은 자체 게시판에서 0건이 나옴. 후자는 `manual_check`에 "나라장터로 별도
  수집되고 있으니 실제 문제가 아닐 가능성이 높음"으로 구분 표시됨 - 정상 동작.
- **Selenium 동시 실행 수(`config.MAX_WORKERS_SELENIUM`)**: Streamlit Cloud
  무료 플랜은 메모리가 넉넉하지 않다. 자꾸 수집이 중간에 멈추면 이 값을 1로
  낮춰서 안정성을 우선하는 것을 고려.
